1. Problem and what I built

Sub-Saharan Africa, Rwanda included, has very few specialist dermatologists, so most people with a suspicious skin lesion are seen by a clinician or health worker without dermatology training. I built a web prototype that helps that first step. A health worker uploads or takes a photo of a lesion and the system returns: the most likely of 7 lesion classes with a probability for each, an uncertainty level, a "Review recommended" warning when the model is unsure or sees any sign of melanoma, and a Grad-CAM heatmap showing which part of the image drove the result. Every case is stored so it can be reviewed later. The tool does not diagnose. It is meant to help decide which cases need a specialist.

The stack is Python with PyTorch (EfficientNet-B3), FastAPI, SQLAlchemy with SQLite for development and PostgreSQL in Docker Compose for production, and React (Vite) for the interface. The model was first trained on HAM10000 (10,015 dermoscopy images, 7 classes) and then fine-tuned with dark-skin photos (Section 4.5); the fine-tuned version is the one deployed.

3. System design and code structure

The backend follows a layered design so that each part can be tested and replaced on its own:

  • API layer (api/routers): thin FastAPI routes for system, auth, screening and cases. They only translate HTTP to service calls.
  • Service layer (services.py): AuthService and ScreeningService hold the business logic, for example "validate, classify, explain, decide review, store".
  • Domain and ML layer (ml/): abstract interfaces LesionClassifier and Explainer with concrete EfficientNetClassifier and GradCamExplainer; ReviewPolicy decides the review flag; ModelConfig loads the model contract.
  • Data layer: UserRepository and CaseRepository wrap SQLAlchemy; ImageStore handles files.
  • Composition root: AppContainer builds every object once at start-up and FastAPI injects them with Depends.

Design choices I can defend: image checks use the Strategy pattern (each check is a QualityCheck subclass run by ImageValidator, so a new check is one new class); the model sits behind an abstract interface, so a new model or a test fake plugs in without touching the API; the repository pattern keeps SQL out of the services, which is why moving from SQLite to PostgreSQL needed only a configuration change; and domain errors (AppError and subclasses) map to HTTP codes in one place instead of in every route. The frontend mirrors this with an ApiClient class, a SessionStore and two hooks (useSession, useCaseHistory). The database has the four tables from the proposal ERD: users, cases, classification_results and explainability_maps.

4. Algorithms

4.1 Classifier

EfficientNet-B3 pretrained on ImageNet, final layer replaced with 7 outputs, 300 x 300 input with ImageNet normalisation. Training used AdamW, a cosine learning-rate schedule, a class-weighted loss (about 67% of HAM10000 is one class, common moles), augmentation, and early stopping on validation macro F1 (14 epochs). MobileNetV2 with the same setup is the baseline. The split is by lesion, not by image, so the same lesion never appears in two sets (test set: 1,441 images).

4.2 Uncertainty (Monte Carlo Dropout)

The backbone runs once; the classifier head runs 10 times with dropout switched on, and the softmax outputs are averaged. Uncertainty is the entropy of the averaged distribution, H = -sum p log p. Running only the head 10 times keeps the cost low (one backbone pass instead of ten).

4.3 Review rule

A case is flagged for clinician review when entropy is at least the 80th percentile on the validation set (0.600 for the deployed v1, 0.413 for v0) or the melanoma probability is at least 0.05. The low melanoma threshold is deliberate: missing a melanoma is far worse than an extra referral. Both thresholds were chosen on validation data only.

4.4 Explainability and calibration

Grad-CAM uses the last feature block and the top predicted class, run in evaluation mode. I also fitted temperature scaling (T = 2.017 on validation), which lowered the expected calibration error on the test set from 0.095 to 0.021. It is stored in the model configuration but not yet used by the app, because it raises the review rate from 31.9% to 35.8%.

4.5 Dark-skin fine-tuning

HAM10000 has no skin-tone labels and comes mostly from lighter-skinned patients, while the users in Rwanda will mostly have Fitzpatrick V-VI skin. I ran three experiments, each with a pass/fail rule written before the run:

  • Phase 3 (more data of the same kind): adding PAD-UFES-20 phone photos raised phone-photo accuracy from 34.1% to 80.2%, but false alarms on 410 benign dark-skin lesions rose from 1.7% to 31.2%. Not deployed.
  • Phase 4, run 1 (train on dark skin): 139 Fitzpatrick17k images of skin types IV-VI, measured by 5-fold cross-validation. Dark-skin accuracy rose from 28.1% to 81.3% and dark-skin melanoma sensitivity from 37.5% to 70.0%, with HAM10000 macro F1 unchanged (0.732 to 0.741). But false alarms on the benign dark-skin set rose from 1.7% to 38.0%. The surviving dark-skin images are almost all cancers (84 BCC, 40 melanoma, no moles), so the model learned "dark skin means cancer". Not deployed.
  • Phase 4b (tuning with a locked test set): 20% of the dark-skin images and half of the benign dark-skin patients were locked away and used once at the end. Benign dark-skin lesions were added to training with a loss that pushes probability away from the cancer classes, and a fixed list of changes was tried one at a time, each kept only if it improved cross-validated dark-skin macro F1. Adding benign dark-skin lesions cut development false alarms from 21.9% to 1.4%; adding Fitzpatrick III photos gave the largest accuracy gain; more dark-skin share, longer training, class balancing and label smoothing did not help. The loop hit its 8-hour limit before the last two planned changes.

7. Discussion

Change to FR-09. The proposal planned a login screen. For a prototype that handles only anonymous, non-identifying images, a login step adds friction for the user and for demos, and protects little. I kept the security underneath: the browser creates a random anonymous account on first use, every prediction and history call still needs a JWT, and one visitor cannot see another visitor's cases. The trade-off is that clearing browser data loses access to old cases. A real deployment with named health workers would add the login screen back, which is a small change because the auth service and endpoints already exist.

Accuracy target. 74.6% balanced accuracy is below the 88-93% I expected. Many published HAM10000 results use image-level splits (the same lesion can appear in training and test), ensembles or extra data. My lesion-level split is stricter, and I report the number as it is rather than tune on the test set.

Dark skin. This is the most important limitation and my main personal goal. The experiments show that more light-skin data does not help dark skin, and that a small dark-skin set can raise accuracy but also creates new shortcuts unless benign dark-skin cases are included. Public dark-skin data with lesion labels is very scarce. Adding benign dark-skin examples fixed most of the shortcut, and the deployed model is much better on a small locked dark-skin test, but 29 web photos with no moles cannot show that it is safe. I do not claim the system works on dark skin.

Other limitations. HAM10000 is dermoscopy, while health workers will mostly use phone cameras (the original model reached only 34% on phone photos, and the deployed model has not been tested on them). The model was never tested by clinicians. Squamous cell carcinoma is not one of the 7 classes. No real patient data was used.

8. Future work

  1. Collect consented, biopsy-confirmed photos from Rwandan clinics with ethics approval (Rwanda National Ethics Committee), with Fitzpatrick labels, and report sensitivity by skin type.
  2. Evaluate on the Diverse Dermatology Images dataset (I have access), finish the two untried tuning steps with a new locked test set, and add phone-photo data to training.
  3. Refit temperature calibration for v1, wire it in, and record self-reported skin type per case so fairness can be monitored.
  4. Run a usability study with community health workers and a pilot with clinicians before any real use.
